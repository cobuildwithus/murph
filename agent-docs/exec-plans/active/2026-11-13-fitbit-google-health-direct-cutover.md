# Fitbit to Google Health as ordinary Junction sources

## Outcome and incident

Admit Google Health as an ordinary Junction source as soon as it is authorized and connected. Attempt to revoke an active legacy Fitbit source through the existing claim/recovery boundary, so one feed remains going forward; overlapping historical facts use Murph's generic multi-source readers.

One dual-source connection is stuck behind migration-only readiness checks, and encrypted webhook work is held in the Queue/DLQ. Two Fitbit daily finalization values are null; Google Health lists 26 resources, including `body_temperature` but not `body_temperature_delta`. The latter 11 Fitbit-produced resources are present. These facts explain the current stall but are not new admission requirements.

## Overlap verdict and code evidence

**Same kind of overlap as other Junction/direct/health-store pairs.** Strict non-overlap of canonical intervals is not a generic Murph invariant. The vault retains source-specific facts; product summaries resolve or partition them. This accepts two raw records for one physical observation, just as Apple Health may relay Garmin or WHOOP data.

## Rule and failure behavior

- Remove the Google Health special admission branch from `packages/device-syncd/src/providers/junction.ts::isJunctionSourceAdmittedForImport`. No cutoff, coverage fence, finalization metadata, resource parity, fresh-fact gate, or historical-backfill prerequisite. Google Health history is imported normally and may overlap retained Fitbit history. Keep generic source identity, connected/disconnected and lifecycle-epoch checks, exact historical job binding, and canonical import receipts.
- Google Health authorization starts the existing `fitbit-migration-cutover.ts` completion attempt; the current bounded hosted maintenance pass also revisits already-authorized pairs. Its connection lock, dirty drain, exact claim, provider revoke, definitive access check, and terminal source update remain. Relax its eligibility to connected Google Health plus active Fitbit. During the brief dual-source interval, both may import under ordinary rules. If revocation is confirmed, Fitbit stops; no new Fitbit historical pull is scheduled.
- Correct uncertain revoke handling: a revoke error followed by a **failed definitive check** keeps the claim fenced for recovery. Restore active Fitbit only when the definitive check says its access remains active. A failed revoke can leave both valid sources active until retry; the generic readers handle their overlap. If Google Health later disconnects, do not resurrect Fitbit; require Google Health reconnection. Reauthorization advances its existing epoch and rejects stale jobs. A Google Health connection without Fitbit needs no revoke.
- Delete the migration-specific Web `migration_pending`/successor-arrival hold and the appended legacy Fitbit backfill. In `wake-service.ts::isHostedJunctionDataSourceUnknown`, permit an exact-source data-less history fetch for **any** source, including Google Health. Recast the existing source-unknown inline-data retry as a generic multi-source ambiguity check; never guess an origin when multiple live sources can write. Source-bearing historical data keeps its original window and imports like any other source. Existing source/lifecycle checks must prevent a new Fitbit provider pull from starting after Web has a terminal source row. A Fitbit fact prepared before revocation may commit afterward as an ordinary overlapping fact; generic readers already accept multi-source overlap. It must not resurrect Fitbit or fail Google Health work.

## Progress

- Plan revised after static code and ReviewGPT review. No product code, commit, deployment, or production mutation in this phase.
- Implementation stopped before a product change because the requested post-terminal Fitbit admission guarantee cannot be proved with the existing lifecycle seam. The hosted runner's `listHostedJobConnectionSources` calls Web `fetchSnapshot` and returns a source snapshot; `readJunctionImportSources` uses that result to prepare/filter the import. `commitPreparedJunctionCanonicalImport` then calls the separate vault importer. Web's `withConnectionMutationLock` covers its source-row claim and finalization transaction, but it does not cover the runner's canonical vault write.

An extra runner read immediately before import only moves the same race window. The existing lifecycle epoch check likewise compares snapshots before the write and cannot make Web finalization atomic with vault publication. The plan's instruction to prove no post-terminal Fitbit commit therefore requires a cross-boundary coordination rule or a narrower guarantee. Its "no new state, service, endpoint or overlap helper" shape does not provide that rule. The Phase 4 brief explicitly says to stop and record a wrong plan assumption rather than adding machinery, so partial edits were rolled back.
