# Replace static secrets with OIDC / short-lived credentials

Status: active (2026-11-16). PRs: #5108 APNs, #5109 Linq canary, #5110 GitHub App KMS, Worker retirement (this PR). Owner asked for: OpenAI via OIDC directly, GitHub
App keys out of CI, Linq canary reset via GitHub OIDC, APNs key out of env,
PlanetScale via GitHub OIDC, and deletion of unused keys.
Evidence: `audit-packages/oidc-static-secrets-investigation.md` (inventory).

## Facts this plan rests on (checked 2026-11-16)

- OpenAI API workload identity federation: exchange at
  `POST https://auth.openai.com/oauth/token` (RFC 8693 token exchange,
  `identity_provider_id`, `service_account_id`), tokens last at most 1 hour and
  never outlive the subject token, no refresh token. **Arbitrary OIDC issuers
  are not supported; Vercel is not a supported issuer.** Google Cloud
  (`iss=https://accounts.google.com`, custom audience, map `sub`) and GitHub
  Actions are supported. WIF tokens cannot call the Admin API.
- `openai@6.45.0` (our pinned SDK) has a built-in `workloadIdentity` client
  option (`identityProviderId`, `serviceAccountId`,
  `provider: { tokenType: 'jwt' | 'id', getToken }`, `refreshBufferSeconds`
  default 1200). The SDK performs the exchange and refresh.
- We already run Vercel OIDC → Google STS → service-account impersonation →
  Cloud KMS in `apps/web/src/lib/hosted-crypto/gcp-kms.ts`, with an
  `asymmetricSign` operation, deadlines, shared refresh and redaction.
- Cloudflare Workers/Containers have no ambient workload identity. The Worker
  already authenticates to Web with a body-bound signed callback
  (`HOSTED_WEB_CALLBACK_SIGNING_PRIVATE_JWK`, `web-callback-auth.ts`), and Web →
  Worker uses Vercel OIDC.
- PlanetScale: GitHub Actions OIDC → short-lived PlanetScale service token
  (changelog 2026-11-05; `pscale oidc-trust` CLI 2026-11-12). Postgres roles can
  be created with `pscale role create <db> <branch> <name> --ttl 1h
  --inherited-roles <role>`. Postgres wire auth itself is still password based.
- GitHub App private keys can only be generated by GitHub (we cannot supply our
  own public key), so a KMS signer needs the PEM imported once.
- Murph-cloud's Cloudflare deploy re-renders Worker secrets from GitHub secrets;
  `apps/cloudflare/scripts/deploy-retired-inference-secrets.ts` holds a
  `retiredSecrets` set that the deploy deletes as a native version patch.

## Design decisions

1. **One KMS: Google Cloud KMS** (project already federated) for every signing
   key we move (GitHub Apps from CI, APNs from Web). We do not add Vercel KMS
   (beta, second key system, new SDK) because Web already has a Google KMS
   adapter with `asymmetricSign` and Vercel OIDC federation.
2. **OpenAI identity chain for Web:** Vercel OIDC → Google STS → impersonate a
   dedicated GCP service account that holds only
   `roles/iam.serviceAccountOpenIdTokenCreator` on itself → IAM Credentials
   `generateIdToken(audience=<OPENAI_WIF_AUDIENCE>, includeEmail=true)` →
   OpenAI SDK `workloadIdentity` (`tokenType: 'id'`). OpenAI provider =
   Google Cloud preset, mapping `sub` = the GCP service account unique ID.
   - Two OpenAI service accounts (and two GCP SAs) so usage and blast radius
     stay separate: `web-classifiers` (first-contact admission + ack reaction
     classifiers) and `hosted-assistant` (Cloudflare runner traffic).
   - The two dedicated classifier key names
     (`HOSTED_ONBOARDING_LINQ_FIRST_CONTACT_ADMISSION_OPENAI_API_KEY`,
     `HOSTED_LINQ_ACK_REACTION_OPENAI_API_KEY`) collapse into the
     `web-classifiers` service account.
3. **OpenAI for the Cloudflare runner (broker):** a new internal Web route
   mints a `hosted-assistant` OpenAI access token and returns
   `{ accessToken, expiresAt }`. The Worker calls it with the existing signed
   Worker → Web callback auth (no new credential), caches per isolate until
   `expiresAt - 10 min` with single-flight refresh, and
   `runner-egress-intercept.ts` injects `Authorization: Bearer <token>` exactly
   where it injects the API key today. Containers keep the placeholder; the
   real token never enters a container. Broker failure fails closed (OpenAI
   calls error) and raises the existing OpenAI authorization alert; there is no
   static-key fallback in production.
   - Root credential that remains: the Worker's callback signing key, which we
     own and can rotate. Net: one fewer third-party static key in Cloudflare,
     Vercel, and murph-cloud GitHub secrets.
4. **GitHub App installation tokens from KMS:** new Google WIF pool for GitHub
   Actions (`iss=https://token.actions.githubusercontent.com`), attribute
   condition pinned to our org and the two repos, attributes for `repository`
   and `workflow_ref`. One RSA_SIGN_PKCS1_2048_SHA256 key per App (imported).
   IAM: `roles/cloudkms.signer` on each key only for the principalSet of the
   workflows that use that App. A local composite action replaces
   `actions/create-github-app-token`: `google-github-actions/auth` (pinned
   SHA, direct WIF, no SA key) → KMS `asymmetricSign` over the RS256 JWT
   signing input → `POST /app/installations/{id}/access_tokens` with explicit
   `repositories` and `permissions` → mask and output the token. Jobs gain
   `id-token: write` only where they mint an App token.
   Apps: FROG (friction-log, pr-head-draft-reset), TEMPORAL_COMPATIBILITY
   (temporal-compatibility, temporal-web-deployment-admission,
   junction-wearable-canary), NATIVE_ANDROID_E2E, NATIVE_IOS_E2E.
5. **Linq canary reset via GitHub OIDC:** the Web reset/status route verifies a
   GitHub Actions ID token (JWKS from
   `https://token.actions.githubusercontent.com/.well-known/jwks`) with exact
   `iss`, `aud` (dedicated value), `repository`, `repository_owner`,
   `workflow_ref` (main branch of `linq-production-canary.yml`),
   `event_name` allow-list, and `ref`. Keep the existing fixed canary-target
   restriction and add `jti` one-time use if replay protection is not already
   provided by the route. Remove both canary reset secret names afterwards.
6. **APNs via KMS:** import the APNs `.p8` (P-256) as
   `EC_SIGN_P256_SHA256`; `apple-push/send.ts` signs the provider JWT through the
   existing GCP KMS adapter (DER → JOSE r||s), keeps the 40-minute reuse cache,
   and treats KMS failure as `failed` (same as missing credentials today).
   `APNS_KEY_ID`/`APNS_TEAM_ID` stay; `APNS_PRIVATE_KEY` is removed.
7. **PlanetScale migrations via GitHub OIDC:** `hosted-web-contract-migrations`
   (`production-contract-migrations` job) exchanges GitHub OIDC for a
   short-lived PlanetScale service token, creates a role with `--ttl 1h`
   inheriting the migration/schema-owner role, runs migrations with that DSN,
   and deletes the role in an `always()` step. TTL bounds a leaked or orphaned
   role. Removes `HOSTED_WEB_DIRECT_DATABASE_URL` from GitHub. Spike first on a
   non-production branch to prove `--inherited-roles` can carry the DDL rights
   our migrations need; if not, stop and report. The Cloudflare database
   monitor token stays (Workers cannot use GitHub OIDC; it is metrics-only).
8. **Delete unused keys:**
   - Vercel (no code reader on main or murph-cloud): `WHATSAPP_VERIFY_TOKEN`,
     `HOSTED_MEMBER_RESET_ADMIN_TOKEN`, `HOSTED_BILLING_BACKFILL_SECRET`,
     `MURPH_SUPPLEMENT_DB_URL`, `VERCEL_AI_API_KEY`, `WHOOP_CLIENT_SECRET`,
     `WHOOP_CLIENT_ID`, `KERNEL_API_KEY_DEV`,
     `HOSTED_AUTH_TWILIO_MESSAGING_SERVICE_SID`, Preview `TEMPORAL_API_KEY`.
     Env removal does not redeploy; current code does not read them.
   - Cloudflare Worker: add unused names to `retiredSecrets` and remove them
     from murph-cloud's render step, then delete the murph-cloud GitHub
     secrets. Candidates: `BRAVE_API_KEY`, `EXA_API_KEY`,
     `WHOOP_CLIENT_SECRET`/`_ID`, `OURA_CLIENT_SECRET`/`_ID`,
     `CLOUDFLARE_IMAGES_API_KEY`, plus any Garmin/Strava names with no reader.
   - Retired envelope keys (`HOSTED_EXECUTION_AUTOMATION_RECIPIENT_PRIVATE_JWK`,
     `HOSTED_EXECUTION_PLATFORM_ENVELOPE_KEY`): delete only after proving no
     retained snapshot or recovery path can still need them.

## Rollout order (each step reversible until the old key is revoked)

1. Unused-key deletion (Vercel now; Worker via the next murph-cloud deploy).
2. Infra (additive): GitHub WIF pool/provider, KMS keyring/keys/import jobs,
   OpenAI GCP SAs, PlanetScale OIDC trust.
3. Owner one-time steps: OpenAI dashboard provider + 2 mappings; generate new
   GitHub App keys and run the import script; import the APNs key.
4. Ship code with the new path preferred and the old secret still present.
   Verify in production (canary run, App-token workflows, a real APNs push,
   OpenAI calls on Web and runner, one migration run).
5. Remove old secrets from Vercel/Cloudflare/GitHub; revoke old GitHub App
   keys, the OpenAI API keys, and the old APNs key.

Production never silently falls back from a failed federation exchange to a
static key: once the new path is configured, the static key is not consulted.

## Failure modes considered

- OpenAI/Google outage of the exchange: SDK refreshes 20 min before expiry, so
  a short outage only matters after the cached token ages out. Broker caching
  in the Worker uses the same margin.
- Clock skew: token expiry checks use `expires_at` with margin.
- Untrusted PR code: OIDC-minting jobs never run fork PR code; existing
  trusted-controller boundaries stay.
- Key import: the PEM touches only the owner's machine; the import script wraps
  it with the KMS import job and never prints it.

## PlanetScale decision (2026-11-17): not now

`pscale oidc-trust providers show github_actions` (pscale 0.353.0) lists only
`repository_id` and `repository_owner_id` as matchable claims: no `ref`,
`workflow_ref`, `environment` or `sub`. Today `HOSTED_WEB_DIRECT_DATABASE_URL`
is a `production` environment secret whose deployment branch policy is
protected branches only, so a workflow on an arbitrary pushed branch cannot
read it. A trust that can create schema-owner-capable roles but can only be
pinned to the repository would let any branch workflow mint one. That is weaker
than the current control, so the migration DSN stays an environment secret.
Revisit when PlanetScale trusts can match `ref`/`environment`/`workflow_ref`.

## OpenAI decision (2026-11-17): owner dropped the Google hop

Owner: the Vercel → Google STS → generateIdToken → OpenAI chain plus a Worker
broker is too complex and brittle. Codex run stopped; the two GCP service
accounts `openai-web` / `openai-hosted-assistant` were deleted (no roles were
ever granted beyond the token-creator binding). Follow-up (2026-11-17): owner
chose to leave OpenAI as is, with no key lockdown or OpenAI support request. If
it is revisited: a locked-down key, OpenAI accepting Vercel's issuer directly,
or AI Gateway OIDC for Web calls.
