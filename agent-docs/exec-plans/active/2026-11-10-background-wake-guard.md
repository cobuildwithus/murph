# Background wake guard and alert escalation — implementation plan

Status: planning only. No implementation, production mutation, or rollout is authorized by this record.

## Outcome and evidence

Stop repeated autonomous starts from consuming unbounded container capacity and money while preserving immediate member-awaited work, the unbound standby container, and the ten-minute foreground idle window. Three independent loops in nine days show that lane-specific retry fixes do not establish a fleet invariant. The November 10 alert opened after 17 minutes, but its six-hour reminder let the loop continue. The existing thresholds and reminder are in `apps/web/src/lib/hosted-runtime-log/runaway-alert-monitor.ts:18-32`; the cron already runs it in `apps/web/app/api/internal/hosted-runtime/latency-alert/cron/route.ts:18-66`.

Exclude member-hours with at least 25 invocations on the known November 5 and 10 incident UTC days (one and four hours respectively); November 2 is outside this seven-day window. ## Choke point and chosen design (under 40 lines)

1. Put the bound at Web's **new runtime-owner claim**, not at the runtime's `nextWakeAt`. Temporal reads Web's durable workspace and mailbox facts, selects default/system/retention work, and calls Worker ensure-processing (`agent-docs/references/hosted-temporal-orchestration.md:611-639`). Worker calls Web `claim` before starting a new target (`apps/cloudflare/src/runtime-processing.ts:95-133`). Web serializes claims on the member row and creates one `starting` owner before any launch (`apps/web/src/lib/hosted-execution/runtime-owner.ts:39-96`). Direct Web ingress uses an existing-owner snapshot or falls through to the same Worker claim (`apps/web/src/lib/hosted-execution/direct-runtime-wake.ts:50-55,125-163`). This covers assistant due, device-sync, system mailbox, and retention starts without interpreting their payloads.
2. Mark a claim as background only when the trusted ensure caller can **positively establish autonomous work**. Direct Web ingress and Temporal's admitted conversation flag bypass without a rate query or wait; the latter already means positive conversation lag (`agent-docs/references/hosted-temporal-orchestration.md:736-743`). An active owner continues through its existing wake/foreground replacement path (`apps/web/src/lib/hosted-execution/runtime-owner.ts:56-70`). The builder must trace ambiguous default continuations, including pending reply and `assistant_delivery`, before tagging them. Ambiguous work bypasses until that proof exists; never infer background from `processingMode` alone.
3. Add only three small fields to the existing `hosted_runtime_owner` row: fixed-window start, admitted background count, and last admitted background start. Under the existing claim transaction/lock, increment on every **new** background claim, including starts that later fail. No new table, queue, runtime-log dependency, or counter in the runner. The dedicated runtime-log DB has a subject/time index (`apps/web/prisma/runtime-logs/schema.prisma:25`) but is diagnostic and asynchronous; querying it on every claim would couple admission to a second database and fail to count lost completions. Existing owner generation and `startedAt` cannot reconstruct a background-only hourly count (`apps/web/src/lib/hosted-execution/runtime-owner.ts:75-95`).
4. In a one-hour window beginning with its first background claim, admit the first **24** immediately. Thereafter, require five minutes since the last admitted background start. Return an explicit `retry_later` with that deadline before any container start; Temporal retains the durable wake and uses its existing signal-aware retry timer. Reset the count when the fixed window expires; a future or invalid clock value must not grant an indefinite block. Count only new starts, not re-wakes of a live owner. The fixed window bounds a continuous loop to roughly 36 starts/hour (up to roughly 72 in an adversarial rolling hour across a reset); at the task's $0.0017 estimate, the steady one-member ceiling is about $1.47/day. This is a cost brake, not a proof that a cause-specific bug is fixed.
5. Foreground signals and reply continuations never wait behind this rule, including typing and direct ingress. A fresh, member-initiated device connection must be classified as member-awaited and bypass; later autonomous backfill continuations count and can wait at most five minutes after the previous background start once that member's window reaches 24. An operator repair that induces a new start every 90 seconds runs without added wait until the member's aggregate background count reaches 24, then can run at most every five minutes; two mailbox items in one invocation do not consume two permits. Validate these exact journeys before enabling the limit. Existing active work and the ten-minute idle timer are unchanged.
6. Keep the current runaway email incident and its persistence/idempotency owner (`apps/web/src/lib/hosted-operational-alert/incident-email-monitor.ts:378-428`). Shorten **this incident's** open reminder to 30 minutes; retain quiet-hours bypass. Add an estimated invocation spend/hour to its aggregate message, without a separate dollar threshold: 25 starts already trigger below a useful dollar threshold. Add a fleet condition to the same monitor: trailing-hour invocations above **3× the median of the preceding seven matching UTC clock hours and at least 50 above it**, with a minimum baseline sample count. It catches distributed subthreshold loops without a new notification service. Do not page on a single missing/partial baseline; report monitor failure through the existing cron failure path.

## Why other placements and policies lose

| Alternative | One reason to reject |
| --- | --- |
| Floor every `nextWakeAt` in the runner | A fresh conversation may need the same wake; the runner cannot see all Web mailbox and retention admissions. |
| Temporal-only rate cap | Web's direct ingress fast path and independently deployed workflows can still start a target. |
| Worker-only in-memory count | Worker instances/restarts do not share a durable per-member count. |
| Query runtime-log DB on each admission | Diagnostic writes are asynchronous and cross a second DB boundary on the latency-sensitive path. |
| One blanket five-minute floor | It slows ordinary device connect and repair bursts from their first wake. |
| Carry attempts in every device hint | It expands the snapshot/hint contract to solve a cost symptom while leaving other loops unbounded. |
| Derive device backoff solely from job age | Age is not attempt history; it can penalize a legitimately delayed first retry. |
| New SMS service or dollar-only threshold | No operator SMS alert channel was found; the current email threshold detects lower spend first. |

## Cold restore and deletion decision

The device recovery hint carries `maxAttempts: max(1, maxAttempts - attempts)` (`packages/assistant-runtime/src/hosted-device-sync-runtime.ts:1114-1129`), but restore enqueues it with `attempts = 0` (`packages/assistant-runtime/src/hosted-device-sync-runtime.ts:1016-1037`; `packages/device-syncd/src/store/jobs.ts:1292-1308`). The ordinary retry ladder is 15 seconds, one minute, five minutes, 30 minutes, then two hours (`packages/device-syncd/src/shared.ts:113`). The generic guard prevents fast container churn but does **not** repair the attempt-history semantic defect. Keep the November 10 validation point fix; in a separate focused follow-up, either carry the exact attempts with versioned validation or derive a monotone retry floor from already retained `availableAt`/history after proving the real failure classes. Do not silently replace the job's bounded ordinary budget with age. Retained-until-success validation presently schedules every 30 minutes (`packages/device-syncd/src/service.ts:1631-1658,2415`), so a deterministically failing set can consume 48 wakes/day forever. Plan a separate narrow terminal-vs-transient classification and decay repeat deterministic failures to daily after a bounded observation period, while preserving accepted work and alerting on a stalled import. The generic guard alone does not address 48/day because it never reaches the 24/hour threshold.

Delete **no** current per-lane correctness guard in this build. In particular, a past cadence guard (`packages/assistant-runtime/src/hosted-device-sync-runtime.ts:1222-1228`), retained validation delay, thumbnail publication retry, and idle snapshot correction protect distinct correctness/recovery contracts. Remove only a demonstrably redundant frequency-only guard if the build finds one; no such deletion is proven by this inspection.

## Failure modes, tests, and rollout

- **Skew:** deploy additive schema and Web readers first, then Worker/parser consumers, then any Temporal producer, then enable Web enforcement only after all producers prove intent. Missing intent means unthrottled foreground-safe behavior. Old Worker must not receive a new request field before it can parse it (`packages/hosted-execution/src/parsers/orchestration-control.ts:253-265`). Keep the old response shape acceptable during Web/Worker convergence. Temporal request-order or timer changes need private workflow replay evidence (`agent-docs/references/hosted-temporal-orchestration.md:541-550`). The runner image has no new dependency; a rollback disables enforcement before reverting readers/schema.
- **Starvation:** the five-minute floor never consumes, discards, or clears a wake. A new accepted conversation and member-awaited continuation bypass it. Prove a hot and cold reply, typing start, device-connect first burst, late backfill, two-item/90-second operator batches, assistant due, device reconcile, retention, and system mailbox continuation. If any paying-user wait acquires the floor, fix classification before rollout. Add a bounded deferred-work age alert or use the existing progress alert if a real delay escapes the five-minute expectation.
- **Clock/concurrency:** use one Web transaction's DB timestamp and member row lock for count, last start, and decision. Test simultaneous claims, failed starts, hour-boundary reset, future timestamps, clock rollback, and old/null columns. Never hold the transaction across Worker/container I/O. Invalid state fails to a bounded diagnostic and foreground-safe retry, not an endless defer.
- **Focused proof:** red/green Web PostgreSQL claim tests; wire parser compatibility tests; Worker `retry_later` and direct-ingress tests; alert incident/reminder/idempotency tests and aggregate fleet-baseline SQL test; one hosted-local end-to-end cold restore/repeated due wake with a foreground message interleaved. Run relevant tests and typechecks per `agent-docs/operations/verification-and-runtime.md`. This is risky runtime behavior, so use the required ReviewGPT gate on the stable pushed build head when the parent later authorizes a PR (`agent-docs/operations/completion-workflow.md`).
- **Production proof after authorized deployment:** count-only, time-bounded runtime-log aggregates compare per-member-hour p99/p99.9/max, guard deferrals, accepted foreground claim latency, reply/typing p95/p99, device-connect completion time, pending-work age, and fleet invocations against the pre-rollout baseline. Check that runaway incidents open by the existing threshold, repeat at 30 minutes while open, and clear only after recovery. Verify no increase in member-awaited latency before raising enforcement beyond canary scope. Keep alerts active if the guard is disabled. No production mutation is part of this planning task.
