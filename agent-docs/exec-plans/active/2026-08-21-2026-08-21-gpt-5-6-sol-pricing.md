# Update GPT-5.6 Sol allowance pricing

Status: active
Created: 2026-08-21
Updated: 2026-08-21

## Goal

- Charge hosted GPT-5.6 Sol usage against member allowances using OpenAI's
  current promotional Standard and Flex token prices, then ship the change to
  production without changing stored usage records or provider routing.

## Product UX

- Effort: Patch.
- Outcome: Fresh GPT-5.6 Sol usage consumes the current provider-normalized
  allowance amount so members retain the intended included usage; historical
  accounted spend stays fixed.
- Reaches: Existing private, Family-sponsored, and joined-group usage-status
  and pause journeys; there is no new action, copy, or surface.
- Proof: Trace a fresh Sol usage record through served-model resolution, its
  immutable pricing snapshot, the selected period's spend increment, remaining
  capacity, and the existing gate; replay an already-accounted record to prove
  it changes neither stored pricing nor aggregate spend.

## Success criteria

- GPT-5.6 Sol Standard rates are $4.00 input, $0.40 cached input, $5.00 cache
  write, and $20.00 output per million tokens.
- GPT-5.6 Sol Flex applies the existing 50% multiplier, yielding $2.00 input,
  $0.20 cached input, $2.50 cache write, and $10.00 output per million tokens.
- Focused tests cover the exact Standard and Flex rates and calculated cost.
- The web app typecheck and focused usage-allowance test pass.
- The exact reviewed PR head passes required CI and ReviewGPT, is merged, and
  its production deployment is verified.

## Scope

- In scope: GPT-5.6 Sol allowance-accounting rates, pricing-version metadata,
  focused regression coverage, PR review, merge, and Web deployment proof.
- Out of scope: Terra, Luna, Venice, Fast mode, long-context pricing, historical
  repricing, provider routing, schema changes, and member-visible product copy.

## Constraints

- Technical constraints: hosted Codex compacts at 132,000 tokens, below the
  272,000-token threshold for OpenAI's long-context rates; therefore the
  short-context rates are the applicable production rates.
- Product/process constraints: treat this as billing-sensitive logic; keep the
  implementation data-only, preserve immutable historical usage, and complete
  exact-head CI plus ReviewGPT before merge.

## Risks and mitigations

1. Risk: applying the long-context or Fast-mode table would misprice allowance
   consumption.
   Mitigation: use the official Standard short-context table and retain the
   existing explicit Flex multiplier.
2. Risk: shared pricing-version metadata could drift from the rates used for a
   record.
   Mitigation: update the GPT-5.6 version identifiers with the constants and
   assert both versions in focused tests.
3. Risk: old and new Web instances may overlap during rollout.
   Mitigation: both versions accept the same usage-record shape; the only skew
   is allowance cost during the bounded deployment window, with no data
   migration or rollback dependency.

## Tasks

2. Update focused tests for exact Standard and Flex rates and costs.
3. Run the focused test, Web typecheck, and diff/privacy checks.
4. Push a candidate, open the PR, and run ReviewGPT concurrently with CI.
5. Resolve findings, finish the plan, merge, and verify the Web deployment.

## Decisions

- Use the official pricing page at
  `https://developers.openai.com/api/docs/pricing` as the source of truth.
- Keep Flex as a 50% adjustment over the Standard rate constants so the two
  pricing paths cannot drift independently.
- Do not add a long-context branch because the current hosted runtime cannot
  reach that pricing tier before compaction.

## Product UX walkthrough

- Private or Family-sponsored member: an ordinary Sol-backed reply records the
  lower current cost once, preserving more remaining allowance and delaying the
  existing limit notice or pause boundary. Purchased credits are still added
  after included capacity and keep their current semantics.
- Joined-group member: the same record is charged to the existing
  thread-container period, so its used percentage and eventual neutral group
  limit notice advance at the corrected rate without changing owner or
  participant authority.
- Historical and recovery path: the conditional `allowanceAccountedAt` write
  prevents a replay from changing its pricing snapshot or period spend; no
  backfill or repair action is required.
- Evidence: exact Standard/Flex bucket pricing, served-model rerouting,
  conditional write-once accounting, private remaining-capacity/credit gates,
  and thread-container allowed/exhausted gates are covered by the focused Web
  suite. The required hosted-local scheduled-reminder scenario covers persisted
  Flex pricing-version metadata through the production-shaped provider path.
- Difference from the initial plan: Product UX was initially classified as not
  applicable; the specialist review correctly identified allowance quantity and
  pause timing as billing behavior. The implementation scope did not change.
- Verdict: Ready. Both affected journeys preserve their existing promise with
  corrected spend, immutable history, and unchanged recovery behavior.
