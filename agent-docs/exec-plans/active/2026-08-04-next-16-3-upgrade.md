# Upgrade hosted Web to Next.js 16.3

Status: active
Created: 2026-08-04
Updated: 2026-08-04

## Goal

- Upgrade the hosted Web application from Next.js 16.2.6 to the stable 16.3
  release without changing Murph product behavior, weakening validation, or
  widening the dependency surface.

## Success criteria

- `apps/web` resolves the stable Next.js 16.3 release and its matching ESLint
  configuration from the public npm registry.
- The committed lockfile and pnpm supply-chain controls remain consistent, with
  only the explicitly approved exact-package maturity exceptions and no new
  ignored build script.
- Focused Web typechecking, tests, dependency guards, and the production build
  pass on the exact candidate.
- Required ReviewGPT stages and exact-head GitHub Actions pass before handoff.

## Scope

- In scope: Next.js and matching first-party Next tooling, the lockfile, and
  only compatibility corrections directly required by the 16.3 upgrade.
- Out of scope: adopting new 16.3 product features, redesigning routes or UI,
  changing Web runtime ownership, or folding in the separate Vercel build-memory
  PR.

## Constraints

- Technical constraints: preserve the current public package specs, pnpm
  supply-chain verification, route contracts, build validation, and Vercel
  runtime behavior.
- Product/process constraints: use an isolated worktree and PR, keep the diff
  dependency-focused, and do not claim Turbopack memory improvements without a
  production build and exact-head CI evidence.

## Risks and mitigations

1. Risk: a framework minor release changes generated types, routing, bundling,
   or build behavior across the whole Web app.
   Mitigation: inspect the official release notes and package metadata, then run
   the focused Web verification and a production build before publishing.
2. Risk: lockfile resolution silently changes unrelated transitive packages.
   Mitigation: update only the named Next packages, inspect the complete
   lockfile diff, and run the dependency guards and audit.
3. Risk: the upgrade overlaps the open Vercel Standard build-memory PR.
   Mitigation: base this PR on current `main`, keep its diff independent, and
   call out the interaction for later rebase testing instead of importing that
   PR's changes.

## Tasks

1. Confirm the official 16.3 release requirements and current Murph dependency
   ownership.
2. Update Next.js, matching ESLint tooling, and the lockfile with pnpm.
3. Inspect migration output and make only required compatibility corrections.
4. Run dependency, Web typecheck/test, and production-build proof.
5. Commit and push the candidate, open the PR, and run required ReviewGPT and
   exact-head CI gates.
6. Resolve findings, perform the parent final review, close this plan, and push
   the final head.

## Decisions

- Keep this as an upgrade-only PR; new 16.3 capabilities require separate
  product or build-performance evidence.
- The release is younger than the repository's 24-hour maturity window. With
  explicit user approval, admit only the exact official Next 16.3.0 package
  family through `minimumReleaseAgeExclude`; do not add a wildcard or relax the
  global policy.
- Delete the old Next-specific PostCSS override because 16.3.0 now depends on
  PostCSS 8.5.23, above the repository's patched security floor.
- Delete `turbopackMemoryLimit` and its exact-value assertion because Next 16.3
  removed the ignored option from its config schema and types. Keep the existing
  source-map and worker-count settings; the new memory-eviction behavior is a
  framework default and needs no replacement config.
- Set `agentRules: false` because Next 16.3 otherwise creates nested
  `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` files whenever an AI agent starts
  the development server. Murph already owns repository-wide agent guidance at
  the root, so the generated duplicate would only create working-tree churn.
- Extend the existing generated-declaration guard and clean-typecheck stubber
  for Next 16.3's new sibling `root-params.d.ts` import. Keep the allowlist
  exact: the root-params path must share the already-approved Next output
  directory with `routes.d.ts`; arbitrary declaration files remain rejected.
