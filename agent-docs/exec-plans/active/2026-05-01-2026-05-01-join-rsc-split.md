# Move join invite page toward server-rendered RSC islands

Status: active
Created: 2026-05-01
Updated: 2026-05-01

## Goal

- Refactor `/join/[inviteCode]` so the invite page is mostly rendered by server components and server async page data, while browser-only Privy, form, polling, consent, and checkout behavior lives in small client islands.
- Preserve the existing user-visible hosted onboarding behavior, including legal-consent gating, stale-status anti-regression behavior, billing plan selection, and activation polling.

## Success criteria

- The initial join page shell, header, invalid/expired/blocked copy, pricing card layout, and active/activating static panels are server-rendered.
- Client components receive only serializable, minimized props and never receive raw Privy session identity, lookup keys, raw invite phone numbers, or Stripe checkout URLs.
- Legal consent gates checkout/active UI fail-closed until launch consent is current.
- Existing stale verify/status refresh protections remain covered by focused tests.
- Focused hosted onboarding tests, hosted-web typecheck/lint or truthful scoped equivalents, and required audit passes complete or have documented unrelated blockers.

## Scope

- In scope:
  - `apps/web/app/join/[inviteCode]/page.tsx`
  - `apps/web/src/components/hosted-onboarding/join-invite*`
  - Small hosted-onboarding server/client helper modules needed for the split.
  - Directly coupled hosted onboarding tests under `apps/web/test/`.
- Out of scope:
  - Billing route or Stripe service semantics.
  - Privy SDK/auth implementation changes outside the join invite flow.
  - Visual redesign of the join page.
  - Device-sync, Cloudflare, Health Commons, or dashboard `/connect` active work.

## Constraints

- Technical constraints:
  - Server components may not import client-only panel files or pass ordinary function props to client components.
  - The server status read must include the authenticated session identity so it matches the invite status API.
  - Checkout buttons must POST to the existing checkout API route and handle redirect/already-active client-side.
  - Legal consent submission stays client-owned but should reuse server-fetched initial status where practical.
  - Preserve single-flight polling and stale `verify` anti-regression behavior.
- Product/process constraints:
  - Keep copy and visual styling stable unless the component split exposes an actual bug.
  - Preserve unrelated dirty work in the shared checkout.
  - Do not expose direct personal identifiers, secrets, raw credentials, or raw contact data in code, docs, tests, or logs.

## Risks and mitigations

1. Risk: A pure `router.refresh()` island can regress users from checkout/active back to verify during Privy/session lag.
   Mitigation: Keep a small client flow coordinator or server-side monotonic protection, and preserve focused stale-status tests.
2. Risk: Server-rendering the page serializes more data into the RSC payload.
   Mitigation: Build a minimized page model and pass only masked/status presentation fields to client islands.
3. Risk: Legal consent errors accidentally reveal pricing/checkout UI.
   Mitigation: Treat consent read failure as gated/error state and hide checkout actions until `launchGranted`.

## Tasks

1. Split server page model from the current page data read.
2. Extract server-safe shell/header/stage/panel markup from client-only files.
3. Replace broad `JoinInviteClient` rendering with a small coordinator and leaf islands.
4. Update focused page/component tests around status identity, consent gating, stale refresh, and plan selection.
5. Run scoped verification, required audits, and close the plan with the safest available commit path.

## Decisions

- Keep checkout, phone auth, Telegram linking, and consent submission as existing API-backed client flows rather than server actions in this pass.
- Keep a small client coordinator for transient onboarding state; do not force all state into `router.refresh()`.
