# Hosted OpenAI WebSocket capability preservation

Status: completed
Created: 2026-05-27
Updated: 2026-05-27

## Goal

- Preserve Codex's built-in OpenAI Responses WebSocket capability in the hosted
  `hosted-openai` provider wrapper so resumed hosted turns can use the provider
  continuity path instead of replaying large HTTP prompts.
- Keep the hosted wrapper narrow: it exists only to attach Cloudflare runtime
  authority headers and sentinel auth, not to fork OpenAI provider behavior.

## Success criteria

- `hosted-openai` generated config includes `supports_websockets = true` for
  the real OpenAI provider.
- Local hosted test-provider override stays HTTP-only so existing test stubs do
  not need WebSocket support.
- Cloudflare OpenAI egress allows only the Responses WebSocket upgrade path
  with the standard handshake headers, behind the existing sentinel credential
  and runtime write-fence checks.
- Normal `GET /v1/responses` remains blocked, and cache diagnostics remain
  scoped to POST request bodies.
- Focused tests cover the generated provider config and egress policy.

## Scope

- In scope:
  - Operator provider capability metadata.
  - Hosted Codex TOML generation.
  - Cloudflare OpenAI egress policy and focused tests.
- Out of scope:
  - Changing Codex reserved built-in provider semantics.
  - Manual `previous_response_id` plumbing in Murph.
  - Broad hosted runner scheduling, device-sync, or Temporal changes.

## Constraints

- Technical constraints:
  - Preserve Worker-owned OpenAI credential injection; child containers still
    receive only the sentinel credential.
  - Do not expose runtime authority headers upstream.
  - Do not expand provider egress beyond the exact OpenAI paths needed.
- Product/process constraints:
  - Keep the implementation simple, typed, and test-covered.
  - Do not log prompts, request bodies, provider responses, raw IDs, paths, or
    secrets.

## Risks and mitigations

1. Risk: Enabling WebSockets without allowing the Cloudflare egress upgrade
   would add a failed WebSocket attempt before Codex falls back to HTTP.
   Mitigation: land the provider capability and egress policy together.
2. Risk: WebSocket GET requests get treated like POST request bodies by cache
   diagnostics.
   Mitigation: diagnostic emission is limited to POST Responses endpoints.

## Tasks

1. Add typed `supportsWebSockets` provider capability metadata.
2. Emit `supports_websockets = true` for hosted real OpenAI config and keep
   local test overrides HTTP-only.
3. Allow only OpenAI Responses WebSocket upgrade egress in Cloudflare.
4. Add focused tests for config generation and egress behavior.
5. Run scoped verification, required audits, and finish the plan.

## Decisions

- Keep `hosted-openai` as the hosted wrapper because Codex rejects overriding
  reserved built-in provider ids such as `openai`.
- Do not copy every built-in OpenAI field. Preserve only the actual capability
  we dropped accidentally; keep hosted auth/header differences explicit.
- Do not add custom-provider override plumbing for this. The hosted OpenAI
  wrapper is generated by the hosted runtime config path, and preserving the
  one dropped OpenAI capability there is simpler than broadening generic
  provider override behavior.
