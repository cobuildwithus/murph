# Repair hosted-local Docker isolation across macOS contexts and MinIO

Status: completed
Created: 2026-08-26
Updated: 2026-08-26

## Goal

- Make hosted-local E2E Docker isolation retain the selected local Docker
  engine and standard Buildx discovery on supported macOS hosts while keeping
  registry authentication out of the isolated config, and stop applying the
  Linux-only MinIO UID/GID override on macOS.

## Success criteria

- An isolated Docker config carries only the active non-default context plus
  the exact context metadata/TLS material required to resolve it; registry
  auth and credential-helper settings are absent.
- Docker CLI plugin discovery includes the Apple Silicon Homebrew directory on
  macOS without changing other platform candidates.
- MinIO uses the host UID/GID override on Linux only.
- Focused platform/config tests fail on the pre-fix implementation and pass on
  the completed implementation.
- Hosted-local harness typecheck, package coverage, and package-boundary proof
  pass; exact-head review and required CI evidence are recorded in the PR.

## Scope

- In scope: hosted-local Docker config preparation, Docker CLI plugin discovery,
  MinIO Docker user arguments, focused tests, and the owning verification docs
  if the durable contract needs clarification.
- Out of scope: Docker daemon installation or reconfiguration, registry
  authentication, container image changes, production runtime behavior, and
  the legacy Frog autofix engine.

## Constraints

- Technical constraints: preserve only the active context boundary; do not copy
  registry auth, credential stores, or unrelated Docker contexts; keep
  temporary files owner-only and existing cleanup/readiness behavior intact.
- Product/process constraints: make the smallest root-cause repair, preserve
  unrelated work, use the sanctioned worktree/PR path, and leave this
  trust-boundary repair for human merge review.

## Risks and mitigations

1. Risk: copying the host Docker configuration leaks registry credentials.
   Mitigation: construct a new minimal config from the validated context name
   and copy only that context's hashed metadata/TLS directories.
2. Risk: a platform-specific fix regresses Linux CI or custom Docker configs.
   Mitigation: inject platform/config inputs at narrow helpers and cover Linux,
   macOS, default-context, malformed-config, and custom-config cases.
3. Risk: context preservation leaves temporary credentials behind.
   Mitigation: retain the existing owner-only temporary directory and stack
   cleanup lifecycle; do not create a second persisted state owner.

## Tasks

1. Add focused failing tests for minimal context preservation, Apple Silicon
   plugin discovery, and Linux-only MinIO UID/GID arguments.
2. Implement the smallest helper changes at the existing Docker/MinIO owners.
3. Run focused tests, hosted-local harness typecheck/coverage/package-boundary,

4. Commit, push, open a draft PR bound to Frog issue #2328, and run the required

## Decisions

- Preserve context by its Docker-owned SHA-256 directory identity rather than
  copying the whole host Docker config or adding another configuration owner.
- Prefer an explicit `DOCKER_CONTEXT` override to the saved `currentContext`,
  matching Docker CLI precedence while still sourcing only the selected
  context's material from the host config directory.
- Treat this as internal developer tooling with no user-facing Product UX or
  changelog entry, but as a trust-boundary change requiring final ReviewGPT and
  human merge review.
- Logged the reproducible, unrelated runner-bundle byte-budget failure through
  Frog because it blocks the production-shaped E2E before this repair's Docker
  entrypoint can run.
